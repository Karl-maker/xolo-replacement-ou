# Contributing

All collaboration is welcome. Whether you're fixing a bug, improving existing functionality, updating documentation, or suggesting a better approach, your contributions are appreciated.

## Before You Contribute

**Bug fixes and improvements are welcome without prior approval.** Feel free to open an issue or submit a pull request for these changes.

**For new features, please contact the maintainer before starting implementation.** This helps ensure proposed features align with the project's direction and avoids unnecessary work. Open an issue to discuss the idea, scope, and proposed approach before submitting a feature pull request.

If you're unsure whether a change qualifies as a new feature, feel free to ask.

## How to Contribute

1. Fork the repository and create a branch for your changes.
2. Make your changes, keeping them focused and consistent with the existing architecture.
3. Add or update tests where appropriate.
4. Run the relevant tests and checks before submitting.
5. Open a pull request describing what changed, why it was needed, and how it was tested.

For significant bug fixes or architectural improvements, opening an issue first can help establish context, but it isn't required.

## Developer Certificate of Origin (DCO)

All contributions must comply with the [Developer Certificate of Origin (DCO)](https://developercertificate.org/).

By contributing, you certify that you have the right to submit your work under the project's license and agree to the DCO terms.

Sign off each commit using the `-s` flag:

```bash
git commit -s -m "fix: describe your change"
```

This adds a sign-off line to your commit, such as:

```text
Signed-off-by: Your Name <your.email@example.com>
```

Use your real name and a valid email address for the sign-off. Do not sign off on contributions you are not authorized to submit.

All commits included in a contribution must have the required sign-off.

## Code Quality

- Keep changes focused and easy to review.
- Follow the project's existing conventions and architecture.
- Avoid introducing unnecessary dependencies.
- Include tests for new behavior and regression tests for bug fixes where practical.
- Update documentation when behavior, configuration, or usage changes.
- Never include secrets, credentials, or private data in commits.

## Collaboration

Constructive feedback, thoughtful discussions, documentation improvements, bug reports, and code contributions are all welcome.

You don't need to have everything figured out before participating. If you have an idea, find a problem, or see an opportunity to improve the project, start a discussion.

Thank you for helping make the project better.
